AGENT ENGINEERING / Agent 工程

用笔记与历史检索构建 Agent 的外部记忆

简短笔记维护任务主线，历史引用保留原始依据，检索负责把需要的细节重新带回。

2026 年 9 月 9 日

长时间工作的 AI Agent 会积累大量内容：用户要求、代码、工具结果，以及尝试失败的过程。把所有信息一直放进模型输入并不可行，因为上下文容量有限。

一种常见处理方式是把旧内容压缩成摘要。另一种方式是让 Agent 持续维护外部笔记，并在需要时回查历史。后者并没有取消信息提炼，而是增加了持续维护和按需恢复的能力。

笔记仍然是一种信息提炼

摘要和笔记都要决定哪些信息值得保留。“首页已经完成，下一步制作商品列表”无论写在哪种载体中，都没有记录开发首页时的每一次操作。

如果笔记只是另一段更短的文字，却没有维护规则和回查入口，它与摘要的区别可能很小。外部记忆真正需要解决的是：重点怎样保持最新，遗漏的细节怎样找回，以及读取结果怎样重新进入模型输入。

维度以摘要为主的压缩笔记与历史配合
重点如何整理在压缩时生成较短记录。工作中持续维护目标、约束与状态。
细节没有写入时取决于系统是否另有历史读取能力。使用历史工具定位并读取原始记录。
恢复依靠什么保留下来的摘要及其他内容。笔记主线与按需找回的依据。

这不是两种互斥架构。采用摘要的系统同样可以配置历史工具；是否有检索能力，不能仅从一个实验开关是否开启来判断。

一份有用的笔记，需要状态和依据

一个网站任务中，模型发现商品图片无法显示。把几千字报错全部抄入笔记，会增加以后读取的负担；只写“图片有问题”，又不足以恢复工作。更合适的记录可以同时包含当前状态和历史引用。

前几行说明任务接下来怎样推进，最后一行指向可以核对的原始记录。这里的 ID 必须来自实际工具结果，不能由模型随意编造。

笔记负责保留工作主线，引用负责保留通往依据的路径。两者配合，才可能在缩短输入的同时保有找回细节的能力。

读取时，先定位，再取回内容

  1. 已有明确引用

    直接按记录标识读取目标消息，必要时只取相关字符范围。

  2. 只有线索，没有引用

    先搜索特征文本，或按窗口、角色和工具列出记录，再确定目标。

  3. 使用返回结果

    把读回的原话、代码或报错加入后续模型输入，继续完成当前任务。

这类“外部”记忆指信息位于当前模型输入之外，并不说明它一定存放在本机文件或向量数据库中。存储位置与检索算法，需要检查具体实现。

Codex 的 notes 与 history 如何分工

在 rust-v0.153.4 中，notes 提供笔记的列举、读取、搜索、追加和覆盖写入；history 提供窗口列举、消息列举、内容搜索与单条读取。它们分别操作可维护状态和只读历史。[1]

history.read_item 要求窗口 ID 和消息 ID，可限制返回的字符范围。search_contents 的查询参数定义为区分大小写的字面子串，因此不能直接把该接口解释为语义搜索。例如 ImagePathError 与 imagepatherror 是不同的查询条件。[2]

notes 中的路径是服务端笔记空间里的虚拟路径。客户端把读写操作转成带认证的后端请求，而不是默认在本机创建同名文件。这个调用方式也不足以证明后端使用了哪种数据库或索引。[3]

外部记忆需要维护，也有读取成本

笔记可能漏掉关键约束，或者在任务变化后保留过时结论。历史引用也可能指错消息。即使资料能被检索到，模型仍需判断它是否适用于当前问题。

因此，维护重点不只是“写更多”：状态变化后要修订旧描述，关键结论要留下可追溯依据，读取时要限制无关内容。外部记录一旦被读回，就会重新占用上下文。

对于足够长、需要反复核对细节的任务，这套方式提供了清晰的恢复路径。对于本来就能完整放入输入的短任务，额外的写入和检索也会产生开销。评价方案时，应观察关键约束是否保留、依据是否找对、重复工作是否减少，而不能只统计笔记数量。
