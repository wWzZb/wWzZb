Agent 沙箱到底是什么：从受限进程到独立环境

沙箱不是提示词，也不一定是虚拟机。以 Codex 和 TRAE 为例，理解命令执行的权限边界，以及本机受限执行与独立环境的取舍。

2026 年 9 月 17 日 · 官方资料与源码核对

让 Agent 修改项目、运行测试时，它执行的可能就是熟悉的 Python、Node 或 Shell 命令。既然程序和文件都在自己的电脑上，所谓“在沙箱里运行”，究竟多了什么？

多的是一条由执行系统强制落实的边界：命令可以读取什么、修改什么、连接哪里，不再只取决于模型是否听话。这个边界可以围绕本机上的一个进程建立，也可以由独立容器或虚拟机提供。

一、提示词告诉模型规则，沙箱让规则生效

“只修改项目目录”写进上下文，是给模型的行为要求。模型通常会照做，但提示词本身不会改变操作系统的文件权限。如果执行工具仍以完整权限运行，越界命令依然可能造成真实影响。

沙箱则改变命令的执行条件。下面是一个假设规则：允许写入项目目录，允许读取必要的运行库，禁止写入项目以外的私人文档，并限制网络访问。它不是某个产品的完整默认配置，而是用于理解机制的例子。

操作在这套示例规则下由谁落实
读取项目源码允许执行环境的访问控制
修改项目中的业务文件允许执行环境的访问控制
写入未授权的私人文档目录拒绝操作系统的权限或隔离机制
向未放行的网络地址发送数据拒绝所配置的网络控制机制

这里还要区分“只读”和“不可访问”：不能改文件，不等于不能看文件。若目标是保护机密，仅限制写入并不够，还要控制读取和数据外发。

提示词约束模型的选择；沙箱约束执行程序的能力。两者相互配合，但不能互相替代。

二、沙箱通常接在工具的执行端

模型不会直接向硬盘写字节。它先发出工具调用，应用中的执行程序接收请求，再启动命令或调用服务。因此，沙箱通常在“请求即将变成真实操作”的地方接入，而不一定把整个聊天应用或模型放进去。

  1. 模型提出操作

    例如请求运行 python report.py，生成一份报告。

  2. 执行程序确定权限

    结合当前任务配置、允许目录和审批结果，决定在哪里运行、授予哪些能力。

  3. 带着限制启动程序

    使用系统提供的受限进程机制，或把命令交给已准备好的容器、虚拟机。

  4. 系统执行检查，工具返回结果

    程序请求读写文件或访问网络时，相关机制落实限制；执行程序收集输出、错误和退出状态。

所以，“一个工具可以配一个沙箱”是合理的，但不是固定的一对一关系。多个工具可以共用一个任务环境；同一个命令工具也可以按任务选择不同环境。

同时，命令沙箱不自动覆盖所有工具。例如，另一个工具直接调用云端文档接口，它的权限还要由该工具和服务端授权控制。不能因为终端命令受限，就认为所有外部操作都经过同一个边界。

为什么使用起来可能没有明显感觉？

允许范围内的操作本来就能直接完成，不需要每次弹窗。“是否允许发起这次操作”的审批，与“操作运行时具有什么权限”的沙箱是两件事。没有弹窗可能是规则已允许、审批策略允许自动执行，也可能是限制被关闭；单凭体验顺畅，不能判断是哪一种。

三、同一个目标，在不同系统上有不同实现

“包装命令”是理解本机沙箱的一个好入口，但不能理解成只改一段字符串。真正重要的是：包装后的启动过程调用了系统机制，让新进程确实受到约束。

macOS：先应用策略，再运行原命令

Codex 官方说明使用 Seatbelt 策略，并通过 sandbox-exec 启动命令。公开源码中也明确指定系统路径 /usr/bin/sandbox-exec。[1][3]

Python 仍然是 Python，并不需要换成一个“安全版解释器”。变化在于它启动时被施加了策略。后续文件操作能否成功，由系统结合策略和原有权限判断，而不是重新问模型愿不愿意遵守。

Windows：用受限身份启动进程

Codex 官方文档描述了两种原生模式：较强的 elevated 模式使用专用低权限账户、文件权限和防火墙规则；unelevated 模式从当前用户派生受限权限凭证，网络控制较弱。前者需要管理员批准初始化，不表示 Agent 命令以管理员身份运行，也不要求启动微软的 Windows Sandbox 虚拟机。[2]

在本文核对的 Codex 源码版本中，token.rs 调用 CreateRestrictedToken 创建受限凭证，process.rs 使用 CreateProcessAsUserW 携带凭证启动程序。这里的 Token 是 Windows 的身份与权限凭证，可以比作门禁卡，不是模型计费的 token。[4][5]

Linux / WSL2：利用 Linux 的隔离机制

Codex 官方说明，Linux 默认采用 Bubblewrap（bwrap）配合 seccomp：前者帮助建立受隔离的运行视图，后者限制部分系统调用。Windows 上通过 WSL2 运行时走 Linux 路线，而不是原生 Windows 那套实现。[1]

TRAE：区分已公开的能力与未公开的实现

TRAE 的 IDE 沙箱文档（当前称 TraeCode）列出：macOS 使用 sandbox-exec，Windows 使用自研沙箱 SDK，WSL2 / Linux 使用 Bubblewrap 和命名空间。文档没有展开 Windows SDK 的内部系统调用，因此不能把它直接认定为与 Codex 相同的实现，也不能仅凭“SDK”断言它是一台虚拟机。[6]

TraeWork 则明确区分运行模式：Windows 本地 Code 使用本机受限环境，Work / Design 使用隔离的虚拟化环境，并通过受控方式共享项目文件；项目内写入会同步到本地。这个结论有平台和模式前提，不能推广成“TRAE 所有任务都在虚拟机里”。[7]

四、本机受限执行与独立环境，解决的问题不同

形态直观理解主要取舍
本机受限进程使用现有电脑和工具，但缩小进程权限。容易衔接已有项目；需要细致划定可访问资源。
容器给任务独立的文件与进程视图，通常共享所在主机的内核。方便复制和管理环境；隔离能力仍依赖配置。桌面上的 Linux 容器也可能运行在一层虚拟机中。
虚拟机 / 微型虚拟机给任务一套带独立客体内核的运行环境。提供不同的系统隔离边界，但需管理环境、资源和文件交换。

容器并不是小号虚拟机。Docker 官方说明了命名空间、资源控制和能力限制的配合作用；它们共同形成边界，而不是“用了容器”四个字自动保证安全。[8]

对于已有的本地项目，本机受限执行能更自然地复用工具链和文件；对于独立交付、远程执行或多个任务并行，独立环境更容易管理彼此隔离和清理。这是工程取舍，不是所有产品都遵循的统一选型规则。

报告、表格、图片等任务往往更容易被整理成“输入材料—处理—输出成果”，而代码任务可能依赖特定项目的服务、配置和工具链。不过，关键不在输出文件多少，而在于任务与原有环境绑定得有多深。这也解释了为什么同一产品可能针对不同场景采用不同执行方式；它不是对厂商内部决策的证实。

五、独立环境也要管理工具、文件和权限

开发独立沙箱，不只是启动一个空容器或虚拟机。平台还要让任务具备工作条件，并把结果可靠地交还给用户。以下是通用实现方式，不是某个产品的完整架构。

  • 准备工具：通过预装模板提供 Python、Node 等运行时，或按项目安装依赖；模板和缓存可以复用，不必每次从空环境开始。
  • 放入材料：复制文件、拉取 Git 仓库，或把指定目录挂载进去。私有仓库凭证应按需授予。
  • 控制权限：分别决定文件读写、联网范围、凭证访问、内部管理员权限，以及 CPU、内存、磁盘和运行时长。
  • 取出成果：导出文件或代码差异，写到指定输出区，或经授权后推送代码分支。共享目录则可能直接把修改反映到外部。
  • 回收环境：先确认成果已持久保存，再销毁临时环境；不能把任务结束误当作文件已安全交付。

挂载不一定是复制。把真实目录以可写方式挂进沙箱，就可能让沙箱里的修改直接影响真实文件。

Docker 的绑定挂载文档明确指出，默认可写挂载能修改宿主文件；需要只读时应显式设置。它是理解“环境隔离了，为什么文件仍会变化”的具体例子。[9]

隔离得更好，不等于内部可以毫无限制

一次性环境可以允许程序安装软件、修改内部配置，甚至允许弄坏后重建。但如果它拿到了真实服务凭证，又能联网，仍然可能修改外部数据。文件挂载、网络连接和账号凭证，都是通向外界的入口。

例如，分析一份日志副本时，可以只提供输入副本和输出目录，不提供生产密钥。相反，把生产账号交给虚拟机，并不会因为“在虚拟机里”就消除误操作风险。独立环境能让一部分内部权限适当放宽，不能让外部授权变得不再重要。

判断沙箱，看边界，不只看名字

了解一个 Agent 的沙箱，可以追问四件事：哪些工具经过它？程序在哪里执行？哪些文件、网络和凭证真正可用？成果如何回到外部？这些答案，比“安全环境”“自研 SDK”或“容器化”这样的标签更有用。

沙箱的本质，是把执行权限变成可落实的边界。本机进程、容器和虚拟机是实现这个目标的不同手段。产品开发者通常是在现有系统机制上完成策略、启动、授权、资源和生命周期管理，而不是从头开发一台虚拟机。
