AGENT ENGINEERING / Agent 工程

Agent 的行为由谁决定：模型、工具与运行时

从“先记笔记，再切换窗口”这条要求，看清模型决策与程序保证的分界。

2026 年 9 月 9 日

给 AI Agent 一条指令：“上下文快满时，先保存进度，再换窗口。”听起来已经定义了完整流程，但它还没有回答几个工程问题：谁判断快满了？谁真正替换输入？如果模型没写笔记就请求切换，程序会拒绝吗？

Agent 是能借助工具连续完成任务的 AI 助手。它的行为来自模型与运行程序的配合。理解这种配合，需要区分能力配置、工具接口、模型指引和程序控制。

四个层次，负责四类决定

层次负责什么上下文管理中的例子
能力配置决定当前任务启用哪些机制。实验开关、认证、后端支持条件。
工具接口规定模型可以请求哪些操作。写笔记、读历史、请求新窗口。
模型指引引导模型何时使用能力。持续维护记录、交接前补齐进度。
运行程序处理调用并执行具体控制逻辑。计算预算、检查切换条件、替换活动历史。

这里把协调模型请求、工具执行和任务状态的程序称为运行时。模型可能决定“需要查一下旧报错”，运行时则接收这个调用，读取数据，再把结果交回。

提示词表达要求，代码决定如何执行

“先写笔记再切换”可以作为操作指引进入模型输入。它提高模型按预期工作的可能性，但只有程序明确检查了笔记状态，才能把“必须先写好”变成该操作的硬性前置条件。

在 Codex rust-v0.153.4 中，new_context 的处理器只标记切换请求，没有先验证交接笔记完整性。真正的切换由主循环根据是否还需继续、是否收到请求或达到上限来决定。[1]

阅读 Agent 实现时，应分别查“模型被要求做什么”和“程序实际检查了什么”。两份答案未必相同。

代码里有工具，不等于当前任务能调用

工具可用性至少经过两个环节：实现存在，以及当前运行环境满足注册条件。工具怎样提供给模型，也属于接口设计的一部分。

Codex 的历史笔记扩展会检查相关功能配置、OpenAI 提供商和 Codex 后端认证。条件不满足时，它不会返回那套专用工具。history 与 notes 还被标为 DirectModelOnly，供模型直接调用，不通过 code mode 执行器使用。[2][6]

所以，工具组数量、具体操作数量和模型调用入口数量并非同一口径。一个应用提供了普通任务读取工具，也不能据此证明它已经启用专用 history 接口。一次任务中的工具总数，只能说明当时的环境快照。

默认操作流程具体写在哪里

Codex 的模型目录包含 model_messages.token_budget 设置。guidance_message 提供常规记录与恢复指南，reminder_message_template 提供接近预算时的提醒，auto_compact_fallback_prompt 提供基础预算耗尽后的交接要求。[3]

运行程序解析这些设置，把工作指南作为 developer 级上下文注入。developer 在这里表示应用提供的指令层，不是用户必须具备的身份。[4]

打包的 Astra 默认提醒阈值为 6144 token，交接缓冲为 16384 token。token 是模型计量内容的单位；缓冲为交接留出余地，但不会突破模型的完整硬上限。这些数值属于指定版本的模型默认设置，不应当作所有环境永久一致的参数。

这不表示只要设置 true，任何环境都会获得相同能力。激活代码还检查 ChatGPT 登录方式、Plus / Pro / ProLite 计划，以及符合条件的 Codex 后端配置。部分能力在任务启动时决定，不能期待修改配置后旧任务立即更换机制。[5]

配置被读取、启用条件满足、工具实际进入任务，这三个状态应分别确认。它们对应“请求了什么”“允许启用什么”和“最终提供了什么”。

沿着责任边界阅读源码

分析一套 Agent 时，可以从功能入口追到工具注册，再从工具处理器追到主循环；同时查看模型收到的指南和相关测试。这样更容易区分模型选择、应用政策与程序控制。

客户端接口还存在证据边界。看到一次带认证的后端请求，可以确认它如何发出，却不能直接推出服务端采用哪种数据库、怎样管理密钥或保存记录多久。仓库里有测试，也不代表目标环境已经完成了同样的验证。

这种分层方法能把模糊的“Agent 会自动处理”拆成可以检查的实现问题：谁作出决定，谁执行动作，哪里有强制条件，以及失败后还能依靠什么继续。
